What Budgetix Does

Budgetix is a personal finance management platform that lets you track income and expenses across multiple accounts, set budgets, work toward savings goals, and get AI-style insights about your spending — all in one dark-themed, multi-language application.

📊
Dashboard & Analytics
Live KPI cards, 3 chart types, 6-month trend bars, daily trends, projections and burn-rate warnings.
💳
Multi-Account Tracking
Cash, bank, credit card, savings, and investment accounts. Full transfer support between accounts.
📅
Budgets & Goals
Category budgets with rollover, progress bars and alerts. Savings goals with manual contributions.
🔁
Recurring Transactions
6 frequency options, automated hourly posting via scheduler. Pause / resume without deleting.
📈
Reports & Insights
Monthly CSV/PDF exports, 11 insight types auto-generated monthly or on demand.
🔐
Security
JWT + refresh rotation, email OTP, 2FA, OAuth2 Google login, BCrypt passwords, session timeout.

Token Refresh

The frontend HTTP interceptor (auth.interceptor.ts) automatically catches 401 responses, calls POST /auth/refresh with the stored refresh token, and retries the original request. This is transparent to the user.

Google OAuth2

Click Continue with Google on the login page. The browser redirects to Google's consent screen. On approval, Google redirects back to /auth/oauth2/callback with an authorization code. The backend exchanges it for a Google access token, creates or matches a user account, and issues Budgetix tokens.

Scheduler Logic

The RecurringScheduler runs every hour. For each active rule where nextRun ≤ now:

1
Create Transaction
New Transaction record with the rule's amount, type, description, and account.
→
2
Update Balance
Account.balance adjusted (debit for EXPENSE, credit for INCOME).
→
3
Update Budget
Matching Budget.spent incremented if a budget covers this category/period.
→
4
Advance nextRun
nextRun calculated for the next occurrence. If after endDate, rule deactivated.

Categories & Auto-Categorization

Route: /categories

Category Hierarchy

Categories support one level of nesting. System categories are pre-seeded and shared across all users (50+ categories across Income, Expense, and Transfer types). User categories are private and can have any name, icon, colour, and parent.

Auto-Categorization Rules

Each category can have keyword rules. When a transaction is created without an explicit category, the backend scans the description against all keyword rules for that user and assigns the first matching category.

Example rule: Category "Streaming" → keyword "netflix"
Transaction description: "Netflix monthly charge" → auto-assigned to Streaming

Add rules via the Rules button on any category card (including system categories).

Security Model

Authentication Layers

1
BCrypt Password Hashing
Passwords are never stored in plain text. BCrypt with a work factor of 10 is applied at registration and verified at login.
2
JWT Access Tokens (15 minutes)
Signed with HS512 using a 32-char+ secret. Short expiry limits the window of a stolen token. Sent as Authorization: Bearer <token> on every API request.
3
Refresh Token Rotation (7 days)
Stored in the database (refresh_tokens table). On each use, the old token is invalidated and a new pair is issued. Logout immediately deletes the token from the DB, preventing reuse.
4
Email OTP Verification
6-digit time-limited OTP for email verification, password reset, and 2FA. Rate-limited to 3 resends per 24 hours to prevent brute-force.
5
Two-Factor Authentication (2FA)
Optional per user. When enabled, a second 6-digit code is emailed at each login — even if your password is compromised, an attacker still needs access to your email.
6
Session Inactivity Timeout
120-second inactivity timer on the frontend. Automatic sign-out prevents unauthorized access on shared devices.
7
CORS & CSRF
CORS configured to allow only the frontend origin. CSRF protection is disabled because the API uses stateless JWT (not cookies), making CSRF attacks inapplicable.
8
User Data Isolation
Every entity query is scoped to user_id = currentUser.getId(). There is no admin API that could return other users' data through normal endpoints.

Open Banking / Real Bank Linking (Roadmap)

Real bank linking — where Budgetix reads your actual transactions from your bank — requires an Open Banking aggregator like Plaid, Tink, or TrueLayer. Here is exactly how it works.

The 6-Step Open Banking Flow

1
User initiates bank linking
User clicks "Link a real bank account" in the Budgetix UI. The frontend calls the Budgetix backend to create a Link Token (Plaid) or an Auth URL (Tink/TrueLayer). This is a short-lived, single-use token — Budgetix's API key never leaves the backend.
2
Aggregator's secure UI opens
Plaid Link (or Tink/TrueLayer's hosted flow) opens in a modal or redirect. The user selects their bank, enters their bank credentials, and completes any Multi-Factor Authentication their bank requires. Budgetix never sees these credentials.
3
OAuth consent & bank MFA
Modern banks use OAuth2 — the user is redirected to their bank's website, grants consent ("Allow Budgetix to view your accounts and transactions"), and is redirected back. Older banks use screen-scraping via the aggregator (this is being phased out in most regions).
4
Aggregator returns access token
After consent, the aggregator returns a permanent access token (e.g. Plaid's access_token) to the Budgetix backend. This is stored encrypted in the database. It allows Budgetix to fetch data from that bank on behalf of the user indefinitely (until revoked).
5
Budgetix fetches transactions
Using the stored access token, Budgetix calls the aggregator API (GET /transactions in Plaid's API) to retrieve real bank transactions. These are mapped to Budgetix's transaction format and stored in the database, applying auto-categorization rules.
6
Webhooks for real-time updates
The aggregator pushes webhook events to Budgetix's backend when new transactions appear at the bank. Budgetix processes these asynchronously, creating new transaction records without polling. Users see their bank activity reflected in near real-time.

Bank Linking Security

🔒
Credentials never touch Budgetix
Bank credentials are entered only on the aggregator's (Plaid/Tink) or the bank's own OAuth page. Budgetix receives only an opaque access token — it has no visibility into username/password.
🔑
Access tokens encrypted at rest
The access token stored in the Budgetix database is encrypted with AES-256 before storage. The decryption key is loaded from an environment variable — not stored in code.
📋
Read-only scope
The OAuth scope requested from the bank is read-only: accounts:read, transactions:read. Budgetix cannot initiate transfers or make payments on your behalf.
🚫
Instant revocation
Users can unlink a bank account at any time. Budgetix calls the aggregator's token invalidation endpoint and deletes the stored access token. The aggregator informs the bank to revoke consent.
🌐
TLS everywhere
All communication between Budgetix ↔ aggregator ↔ bank uses HTTPS/TLS 1.2+. Aggregator APIs are called only from the backend (server-to-server), never from the browser.
🇪🇺
PSD2 / Open Banking regulatory compliance
EU PSD2 and UK Open Banking regulations mandate that banks support OAuth2-based third-party access via licensed "Account Information Service Providers" (AISPs). Aggregators like Tink and TrueLayer are licensed AISPs, giving them legally sanctioned API access to EU/UK banks.
