01 — Overview

What Is Bank Linking?

Bank linking lets users connect their real bank, credit card, and investment accounts to Budgetix so that transactions are imported automatically — no manual entry, no CSV files. The user logs in to their bank once through a secure overlay; from then on, new transactions appear in Budgetix within hours.

💡

Key principle

You do not connect directly to the bank. You use a licensed financial data aggregator as middleware. The aggregator holds the regulatory licences and handles bank-specific integrations. Your app only talks to the aggregator's clean REST API.

🏦

Automatic Imports

New transactions pulled daily (or on-demand). No manual entry needed.

✏️

Manual Entry Stays

Cash transactions, shared expenses, or corrections are always entered manually. Both modes coexist.

📄

CSV Import Stays

For banks not supported by the aggregator, or for historical data migration.

03 — How It Works

The Full Linking Flow

Bank linking follows a standardised OAuth-style handshake. The user never enters their bank credentials into Budgetix — everything sensitive happens inside the aggregator's secure overlay.

1

User clicks "Connect Bank Account"

The Accounts screen shows an optional button. Clicking it triggers a call to POST /bank/link/token on the Budgetix backend.

2

Backend creates a Link token

The backend calls the aggregator's API with the user's ID and scopes (transactions, balances). The aggregator returns a short-lived link_token (expires in 30 minutes). The backend forwards it to the frontend.

3

Aggregator's secure overlay opens

The frontend initialises the aggregator's SDK (e.g. Plaid Link) using the link_token. A pre-built, hosted UI opens where the user selects their bank and logs in with their bank credentials. Budgetix never sees these credentials.

4

Aggregator returns a public_token

After the user successfully authenticates with their bank, the aggregator's overlay calls a success callback with a one-time public_token. This is safe to pass to your backend — it is useless on its own.

5

Backend exchanges public_token → access_token

The backend calls POST /bank/link/exchange, which exchanges the public_token for a permanent access_token via the aggregator API. The access_token is encrypted and stored in the bank_connections table. It is never sent to the frontend again.

6

Initial sync — transactions imported

Immediately after exchange, the backend fetches up to 90 days of historical transactions and inserts them into the transactions table, tagged with the aggregator's stable transaction ID to prevent duplicates.

7

Ongoing nightly sync

A scheduled job runs every night (or on-demand) per connected account, fetching new transactions using a cursor (a pointer to the last synced position in the bank's transaction stream). Only new transactions are inserted.

04 — Aggregators

Choosing a Financial Data Aggregator

The right aggregator depends on where your users are. All major providers offer a free sandbox environment for development and testing.

Provider Region Model Free Tier Cost (prod) Rec.
Plaid US, CA, UK, EU OAuth + screen-scraping Sandbox only ~$0.30–$1.50 / account / mo Best overall
Nordigen / GoCardless EU (PSD2) Open Banking only Free up to 50 req/day Usage-based, very low Best for EU / free
TrueLayer UK, EU, AU Open Banking Sandbox only Usage-based Good for UK
Yodlee US, global Screen-scraping + OAuth No Enterprise contract Enterprise only

🌍

For global reach → Plaid

Covers 12,000+ banks across US, Canada, UK, and EU. Has official Java SDK, excellent documentation, and Sandbox environment with pre-built test credentials.

🇪🇺

For EU-only → Nordigen (free)

PSD2-compliant, covers 2,000+ EU banks, free tier available. No Java SDK — use their REST API directly. Ideal if your user base is primarily European.

⚠️

Screen-scraping vs Open Banking

Screen-scraping (Plaid legacy, Yodlee) simulates a browser logging into the bank's website. It works with almost any bank but some banks actively block it and it breaks when UIs change. Open Banking / PSD2 uses official bank APIs — more reliable, legally sanctioned in EU/UK, but requires the bank to have implemented the standard. Plaid now uses Open Banking where available.

06 — Backend

Backend Implementation

Three core API endpoints

MethodEndpointPurpose
POST /bank/link/token Create a short-lived link_token from the aggregator. Returned to frontend to open the overlay.
POST /bank/link/exchange Exchange public_token for access_token. Encrypt and persist. Trigger initial sync.
POST /bank/sync/{connectionId} Manually trigger a sync for one connection. Fetch new transactions from aggregator.
DELETE /bank/connections/{id} Revoke access token at aggregator, delete connection record. GDPR right-to-erasure.
GET /bank/connections List all connected institutions for the authenticated user.

PlaidService — key methods

@Service
@RequiredArgsConstructor
public class PlaidService {

    private final PlaidApi plaidClient;
    private final EncryptionService encryptionService;

    /** Step 2: create link token to hand to frontend */
    public String createLinkToken(UUID userId) {
        LinkTokenCreateRequest req = LinkTokenCreateRequest.builder()
            .user(LinkTokenCreateRequestUser.builder().clientUserId(userId.toString()).build())
            .clientName("Budgetix")
            .products(List.of(Products.TRANSACTIONS))
            .countryCodes(List.of(CountryCode.US, CountryCode.GB))
            .language("en")
            .build();
        return plaidClient.linkTokenCreate(req).getLinkToken();
    }

    /** Step 5: exchange public_token → access_token */
    public String exchangePublicToken(String publicToken) {
        ItemPublicTokenExchangeResponse resp =
            plaidClient.itemPublicTokenExchange(
                ItemPublicTokenExchangeRequest.builder().publicToken(publicToken).build()
            );
        // encrypt before returning — never store plaintext
        return encryptionService.encrypt(resp.getAccessToken());
    }

    /** Step 6 & 7: fetch transactions using cursor (incremental) */
    public TransactionsSyncResponse syncTransactions(String encryptedToken, String cursor) {
        String token = encryptionService.decrypt(encryptedToken);
        TransactionsSyncRequest req = TransactionsSyncRequest.builder()
            .accessToken(token)
            .cursor(cursor)   // null on first call → full history
            .build();
        return plaidClient.transactionsSync(req);
    }
}

BankSyncService — deduplication logic

@Transactional
public int sync(BankConnection connection) {
    TransactionsSyncResponse resp = plaidService.syncTransactions(
        connection.getAccessTokenEnc(), connection.getCursor()
    );

    int imported = 0;
    for (Transaction tx : resp.getAdded()) {
        // skip if we already have this plaid_transaction_id
        if (transactionRepository.existsByPlaidTransactionId(tx.getTransactionId())) continue;

        Transaction entity = mapPlaidTransaction(tx, connection);
        transactionRepository.save(entity);
        budgetUpdateService.updateBudgetSpent(entity);
        imported++;
    }

    // save new cursor position for next sync
    connection.setCursor(resp.getNextCursor());
    connection.setLastSyncedAt(LocalDateTime.now());
    bankConnectionRepository.save(connection);

    return imported;
}
07 — Frontend

Frontend Implementation

The aggregator provides a pre-built link UI (an iframe/overlay). You initialise it with the link_token from your backend and handle the callbacks.

Install the Plaid Link script

// angular.json → scripts array
"https://cdn.plaid.com/link/v2/stable/link-initialize.js"

// or load it lazily in the component:
private loadPlaidScript(): Promise<void> {
  return new Promise(resolve => {
    const s = document.createElement('script');
    s.src = 'https://cdn.plaid.com/link/v2/stable/link-initialize.js';
    s.onload = () => resolve();
    document.head.appendChild(s);
  });
}

BankLinkComponent — full flow

@Component({ ... })
export class BankLinkComponent {
  private bankLink = inject(BankLinkService);
  loading = signal(false);

  connectBank(): void {
    this.loading.set(true);

    // 1. Get link token from our backend
    this.bankLink.getLinkToken().subscribe(({ linkToken }) => {

      // 2. Open Plaid Link overlay
      (window as any).Plaid.create({
        token: linkToken,

        // 3. User authenticated → send public_token to our backend
        onSuccess: (publicToken: string, metadata: any) => {
          this.bankLink.exchangeToken(publicToken, metadata.institution).subscribe({
            next: () => {
              this.loading.set(false);
              // refresh account list
            }
          });
        },

        onExit: () => this.loading.set(false),
        onEvent: (eventName: string) => console.debug('Plaid event:', eventName),
      }).open();
    });
  }
}

08 — Deduplication

Transaction Deduplication

This is the most complex part. A user who previously entered transactions manually and then links their bank will end up with duplicates unless you handle it explicitly.

Problem scenarios

  • ✗User manually enters "Starbucks $4.50" then bank imports the same charge
  • ✗Sync runs twice due to scheduler retry — inserts the same transaction twice
  • ✗Pending transaction becomes posted — aggregator returns different IDs

Solutions implemented

  • ✓plaid_transaction_id UNIQUE constraint on transactions table — DB-level dedup
  • ✓Cursor-based sync — only fetches transactions since the last cursor, no re-fetching old ones
  • ✓Manual vs linked badge — imported rows have non-null plaid_transaction_id, helping users spot and merge duplicates
⚠️

Pending → Posted transactions

Banks show transactions as "pending" before they settle. Plaid may return a pending transaction with one ID, then the same settled transaction with a different ID. Handle this by matching on amount + date + description within a 3-day window, and flagging the manual or pending entry as a duplicate rather than creating a new row.

09 — Security

Security Requirements

🔴

Non-negotiable — these are blocking requirements

Failing any of these requirements puts user financial data at risk and may violate banking regulations. They must all be in place before going live.

🔐

Encrypt access_token at rest

The aggregator access_token grants read access to a user's bank. Encrypt it with AES-256-GCM before storing in the database. Store the encryption key in an environment variable or a secrets manager (AWS Secrets Manager, HashiCorp Vault), never in the codebase.

// EncryptionService.java
private SecretKey key = /* from env */;
String encrypt(String plain) { /* AES-256-GCM */ }
String decrypt(String cipher) { /* reverse */ }
🚫

Never send access_token to frontend

The access_token lives exclusively in the backend. API responses to the frontend must never include it — not in connection list responses, not in logs, not in error messages. Only the public_token (one-time, short-lived) ever travels to the backend.

🔒

HTTPS everywhere

All traffic must use TLS 1.2 or higher. This includes the backend API, the Plaid Link overlay callback, and webhook endpoints. In production, terminate TLS at Nginx or your load balancer. Never allow HTTP fallback.

✅

Webhook signature validation

Aggregators send webhooks for events like "new transactions available" or "token expired". Validate the plaid-verification-key header on every incoming webhook. Reject any request that fails validation.

🗑️

User can disconnect at any time

The DELETE /bank/connections/{id} endpoint must call the aggregator's item/remove API to revoke the access_token at source, then delete the local record. Imported transactions are kept (user data), but the bank connection is fully severed.

📋

Explicit user consent

Before opening the link overlay, display a clear consent screen explaining: what data will be read (transactions, balances), how long access is retained, and how to disconnect. Log the timestamp and user ID of this consent for audit purposes.

Complete security checklist

  • ✓AES-256-GCM encryption on access_token with unique IV per record
  • ✓Encryption key in secrets manager — never hardcoded or in application.yml
  • ✓access_token excluded from all DTO responses and logs
  • ✓TLS 1.2+ enforced on all endpoints (Nginx config)
  • ✓Webhook signature validation on every incoming aggregator webhook
  • ✓User isolation — all bank_connections queries filter by user_id from JWT (never by request body)
  • ✓Revoke on disconnect — call aggregator item/remove before deleting local record
  • ✓Consent logging — timestamp + user ID stored when user accepts bank linking
  • ✓Rate-limit /bank/** endpoints to prevent token-stuffing attacks
  • ✓Audit log — log every sync event (user, connection, rows imported) without token data
  • ✓Token rotation — handle ITEM_LOGIN_REQUIRED webhooks by prompting user to re-authenticate
  • ✓Data minimisation — only store fields you display (amount, date, description, category). Do not cache full bank API responses.

What Budgetix does NOT do (scope boundaries)

  • ✗Budgetix never stores or sees bank login credentials — the aggregator overlay handles all authentication
  • ✗Budgetix does not initiate payments or transfers — read-only access only
  • ✗Budgetix does not store full account numbers — only the last 4 digits from the aggregator metadata
10 — Compliance

Legal & Regulatory Requirements

🇺🇸

United States — Regulation E

Plaid holds the required licences and handles Reg E compliance for US users. You must display a clear disclosure before linking (Plaid provides a standard consent template). Users must be able to revoke access at any time.

Handled by Plaid Consent UI required
🇪🇺

European Union — PSD2 + GDPR

PSD2 regulates account access — use a PSD2-licensed aggregator (Nordigen, TrueLayer) for EU users. Banks must have an Open Banking API; screen-scraping is not permitted.

GDPR applies to all financial data. You need a lawful basis for processing (explicit consent), a Data Processing Agreement with your aggregator, a documented right-to-erasure flow, and a Privacy Policy update.

DPA with aggregator required

What you must add to your Privacy Policy

  • ✓Which financial data is collected (transaction history, balances, account metadata)
  • ✓Why it is collected (to provide spending tracking features)
  • ✓How long it is retained (and that users can request deletion)
  • ✓That a third-party aggregator (name it: e.g. Plaid Inc.) is used and has access to the data
  • ✓A link to the aggregator's own privacy policy
  • ✓That Budgetix has read-only access and cannot initiate payments
⚖️

Do you need your own banking licence?

No. The aggregator (Plaid, Nordigen) holds the regulatory licence. You are an "aggregation customer" consuming their API. You do not need an FCA licence (UK), AISP registration (EU), or any US banking licence. However, you must sign a Data Processing Agreement with the aggregator before going live.

11 — Implementation

Step-by-Step Implementation Guide

1

Sign up for a sandbox account

Register at dashboard.plaid.com (or nordigen.com). Get your client_id and secret from the dashboard. Add them to application.yml via environment variables — never hardcode them.

# application.yml
plaid:
  client-id: ${PLAID_CLIENT_ID}
  secret:     ${PLAID_SECRET}
  env:        sandbox   # → development → production
2

Add pom.xml dependency

<!-- Plaid Java SDK -->
<dependency>
  <groupId>com.plaid</groupId>
  <artifactId>plaid-java</artifactId>
  <version>28.3.0</version>
</dependency>
3

Write the Flyway migration

Create V4__add_bank_linking.sql with the three SQL statements from the Architecture section above (bank_connections, bank_accounts, and the ALTER TABLE on transactions).

4

Implement EncryptionService

AES-256-GCM utility class. Key sourced from an environment variable (base64-encoded 32-byte key). This service is used by PlaidService before any token is written to DB.

5

Build PlaidService + BankSyncService

Start with createLinkToken, exchangePublicToken, and syncTransactions. Test each in Sandbox before wiring into the controller. Use Plaid's sandbox credentials (user_good / pass_good).

6

Expose BankLinkController endpoints

Wire the 5 endpoints from the Backend section. Protect all of them with the existing JWT AuthGuard. All queries must filter by the authenticated user's ID — never accept a userId from the request body.

7

Build the Angular BankLinkComponent

Add a "Connect Bank" button to the Accounts screen. On click: call POST /bank/link/token, initialise Plaid Link, handle onSuccess by calling POST /bank/link/exchange, then refresh the account list.

8

Add the nightly scheduler

BankSyncScheduler annotated with @Scheduled(cron = "0 0 3 * * *") (3 AM daily). Iterates over all active BankConnections and calls BankSyncService.sync(). Sends a NotificationService event on completion with count of new transactions.

9

Handle webhook events

Add POST /bank/webhook (public, no auth) — Plaid calls this. Validate the signature header. Handle at minimum: TRANSACTIONS_SYNC_UPDATES_AVAILABLE (trigger sync), ITEM_LOGIN_REQUIRED (notify user to re-link), ITEM_ERROR (mark connection inactive).

10

Update Privacy Policy + add consent screen

Add the Privacy Policy items listed in the Compliance section. Add a consent modal shown before the bank link overlay opens — "By connecting your bank, you authorise Budgetix to read your transaction history via Plaid. You can disconnect at any time in Settings."
