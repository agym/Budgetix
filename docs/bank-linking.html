Concept

What is Open Banking?

A regulated framework (PSD2 in EU, similar laws worldwide) that lets users grant apps read-only access to their bank data — without ever sharing their password.

🔑 THE KEY INSIGHT
Budgetix never sees the user's bank username or password. The user authenticates directly with their bank, which then issues a limited-scope token to Budgetix — exactly like "Sign in with Google".
📋 WHAT YOU CAN ACCESS (read-only)
✓ Transaction history (last 90 days+)
✓ Current & available balance
✓ Account name, type, IBAN / sort code
✓ Pending transactions
✗ Send money (requires payment API — separate license)
✗ Change any account settings

Token consent is time-limited (90 days EU, 30 days US). Users can revoke it from their internet banking at any time — Budgetix loses access immediately.
The Flow

How the link actually happens

A 6-step process the user completes in ~60 seconds. Your backend never touches their credentials.

1

User clicks "Connect Bank"

Budgetix backend calls the provider to create a short-lived link token tied to your app ID — not to the user's bank.

2

Provider widget opens

A secure modal from Plaid / Nordigen loads. The user searches for their bank by name. This runs entirely in an isolated iframe.

3

User logs into their bank

Inside the provider widget, completely isolated from Budgetix. The bank authenticates the user directly, including their own 2FA step.

4

User grants consent

Bank shows exactly what data will be shared (balance, transactions). User explicitly clicks "Allow" — no surprises.

5

Provider returns a public token

Widget closes. A one-time public token is passed to Budgetix's frontend callback function.

6

Backend exchanges for access token

Frontend POSTs public token to /api/banks/link. Backend exchanges it server-side for a long-lived access token — encrypted and stored. Connection is live.

Data Pipeline

What the bank sends — and how it's processed

Raw bank data mapped to Budgetix's Transaction model, deduplicated, and auto-categorized on every sync.

Raw bank transaction (Nordigen JSON)
// GET /api/v2/accounts/{id}/transactions { "transactionId": "2024042801", "bookingDate": "2024-04-28", "transactionAmount": { "amount": "-82.40", "currency": "GBP" }, "creditorName": "TESCO STORES", "remittanceInformationUnstructured": "TESCO STORES 4571 LONDON" }
Mapped to Budgetix Transaction
{ "amount": 82.40, "type": "EXPENSE", "description": "TESCO STORES 4571 LONDON", "date": "2024-04-28", "externalId": "2024042801", // dedup key "categoryId": // auto-matched → "Food" "accountId": // linked Budgetix account }
Processing pipeline (BankSyncService)
1

Fetch from provider

Backend calls provider REST API with stored (decrypted) access token. Returns paginated transaction list.

2

Deduplication

Each bank transaction has a stable externalId. Skip any row already in DB — safe to re-run anytime.

3

Auto-categorization

Run description through existing keyword rules — "TESCO" → Food, "NETFLIX" → Entertainment. Reuses the existing AutoCategorizationService.

4

Save & update balances

Persist new transactions, update account balance, trigger budget checks, fire notifications — same pipeline as manual entry.

5

Webhook (real-time)

Provider calls POST /api/banks/webhook within seconds of a new bank transaction. No polling.

Security

What gets stored — and what doesn't

The model is designed so Budgetix is never a high-value credential target. Even if the DB is compromised, no bank credentials are exposed.

✅ WHAT BUDGETIX STORES
Access token — AES-256 encrypted before DB insert
Account metadata — bank name, account type, last 4 IBAN digits
Transactions — your own normalised copy in your own DB
Consent expiry — to prompt re-auth before token expires
🚫 WHAT BUDGETIX NEVER TOUCHES
Bank username or password — ever
Bank 2FA codes or OTPs
Full card numbers or CVVs
Any payment initiation capability
🔐 ACCESS TOKEN SECURITY
Encrypted at-rest with AES-256 before DB insert
Only decrypted server-side in BankSyncService — never sent to frontend
Expires automatically (90 days EU / 30 days US) — user re-consents via a notification prompt
If revoked by user at their bank → next sync returns 401 → connection marked REVOKED → user notified
🛡️ USER CONTROLS
Disconnect any linked bank from Settings → Linked Banks
Also revocable from bank's own internet banking (independent of Budgetix)
Deleting Budgetix account immediately deletes all stored access tokens
Transaction history is kept locally even after disconnection
Build Plan

What needs to be added to Budgetix

7 components on top of the existing architecture. Most is backend — existing patterns (scheduler, auto-categorization, notifications) are reused.

Backend (Spring Boot)
1

BankConnection entity + Flyway V4

Stores userId, providerName, providerAccountId, encryptedAccessToken, consentExpiry, status (ACTIVE / EXPIRED / REVOKED), linkedAccountId.

2

BankSyncService

Calls provider REST API, deduplicates by externalId, runs auto-categorization (existing service), saves, updates balance.

3

BankController — 4 endpoints

POST /banks/link · POST /banks/{id}/sync · DELETE /banks/{id} · GET /banks

4

Webhook endpoint

POST /banks/webhook — verify signature, trigger sync for the affected account. Real-time imports.

5

Daily scheduled sync fallback

Reuses existing @Scheduled pattern. Catches any missed webhooks. Runs at 06:00 UTC.

Frontend (Angular)
6

Settings → Linked Banks tab

New 4th tab in the existing Settings page. Lists connected banks with status, last sync time, and Disconnect button. "Connect Bank" button opens provider flow.

7

Provider OAuth redirect

For Nordigen: redirect user to provider URL → bank login → redirect back to /oauth2/bank-callback → frontend POSTs token to backend. For Plaid: load JS SDK widget directly.
